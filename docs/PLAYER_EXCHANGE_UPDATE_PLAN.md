## 3. Why server ownership is the critical path

A JWT authenticates a person, not the truth of their local save. A checksum, browser-generated signature, hidden API key, client timestamp, plausible quantity cap or replayed local save does not prove ore was mined. Never create a deposit endpoint accepting a client's claimed balance, mined-cell list, or elapsed extraction time.

Verified Online must own every mint/spend/capacity change on the server, including mining rewards, extraction, building costs/refunds, upgrades, NPC sales, contracts, fuel, inventory transfers, purchases and listings. Server-only trade settlement with client-controlled mining is still exploitable.

No full multiplayer physics server is required, but a resource-awarding command must be independently legal. The client can predict movement/visuals; rewards remain pending until verified. Server validation must use canonical world seed/chart, cell state and player progression, not a client-supplied ore type or yield. A loose movement speed check alone cannot prove an underground path is traversable.

Scope gate: if server-verifying the supported mining/building loop cannot be completed within this update, release only an explicitly labelled isolated market playtest using server test grants, with no link to gameplay inventory. Do not silently substitute that for this plan's completed mine-to-market deliverable. Report the integrated release blocked and what remains.

## 4. Player flows

### Account and campaign choice
1. Guest keeps playing Local with their existing save, offline as before.
2. Account button opens an email-link sign-in screen; explain what will sync. Prefer maintained Supabase auth client over extending bespoke refresh-token handling.
3. After sign-in show two cards: 'Back up this local campaign' and 'Start verified online campaign'. Explain that existing ore stays Local and cannot enter the player exchange.
4. Backups preserve full validated save data and a bounded version history. They are storage, never a mint authority.
5. Online start is one server transaction, unique per account/campaign. Repeated requests return the same campaign. Fresh game baseline: zero credits, zero ore, standard rig and landed mothership; use current game rules, not old market faucet balances.
6. Separate local keys/cache namespaces. Logging out clears account tokens/cache; it does not delete the guest save. Never automatically overwrite one campaign with another.
7. Cross-device play: server revision wins for Online. Local backup restore is an explicit choice with timestamp/device summary and a safety copy of the destination save.

### Earn, list, buy and use
- Online player mines using the supported game controls; server confirms rewards and updates canonical cargo. No local-only grant can be listed.
- A local Market uplink is required to create listings on that planet; seller must be at the surface/uplink and have access to the chosen stock. Keep current ship/warehouse access restrictions.
- Sell source can be Miner, Mothership or active Planet warehouse. Never remote-planet stock. Server checks source existence/access and quantities.
- Seller chooses ore, quantity and price; preview shows exact ore leaving that source, amount reserved and potential proceeds. Posting removes it from available stock into server escrow. It cannot be spent in construction meanwhile.
- Buyer chooses an existing sell listing and quantity. Quote shows seller public handle, unit price, quantity, total and ship capacity after delivery. One confirmation executes purchase.
- Buying requires a verified online campaign, an uplink on the active planet and a docked mothership. Purchases arrive directly in its hold only if sufficient authoritative capacity exists. No automatic dumping into planet storage.
- Seller receives credits while offline. Poll/focus refresh reveals durable receipt; no dependency on a browser being open.
- Cancellation releases only unsold escrow. If original source lacks room or is no longer accessible, return it to a non-spendable 'Market returns' claim record. Claim to an accessible inventory with space. Never silently destroy it or overfill a hold.
- Market returns are not an unlimited warehouse: their ore cannot be sold, built with, transferred remotely or re-listed until claimed. Keep visible claim counts and per-action source/capacity rules. Closing a campaign/account with escrow/returns needs a separate lifecycle policy; no destructive account-delete feature here.
- Empty market is honest. No fake accounts, fake volume, fabricated scarcity or invented live activity.

## 5. Quantities, prices and limits

Game quantities are half units. New market v2 storage uses integer half-units explicitly named quantity_half_units. Display quantity/2 as ore units; .5 always means half an ore, never half a database row. Do not reinterpret old integer market_units as halves.

Credit balances use integer hundredths named credit_minor. UI shows up to two decimals. Price is entered per full ore unit in whole credits for v1; convert to 100 minor units. Buying one half-unit costs price_minor / 2 exactly. Compute totals with server integers; no floating-point settlement. Check integer range before multiplication and never pass unsafe JS bigint values as numbers. Use bounded safe values or validated decimal strings end to end.

Initial limits (configurable server defaults): 10 active listings/account, .5 to 1,000 ore per listing, 1 to 100,000 credits per full unit, 10,000,000 credits listing total. No market fee, no expiry, no matching engine, no bids. List display sorted price ascending then created_at/id. Partial fills allowed in .5 steps. Cancellation idempotent. Rates and prices are beta balances, not token economics.

Use new v2 tables/RPC names or an explicit segregated schema. Existing test wallets/faucet/listings must never be promoted into verified game balances. Preserve historical test data until authorized cleanup. Hide or clearly mark legacy /market as isolated playtest; route the released player exchange to v2 only. Disable new starter grants for the v2 path; bootstrap economy through verified gameplay and existing NPC buyers. Test fixtures/admin issuance belong to staging only.

## 6. Backend shape and API contracts

Use reviewed incremental Supabase migrations. Do not rewrite migrations already applied. Reuse existing RLS/transaction patterns only after auditing them. Suggested entities:
- player_profiles: account ID, non-sensitive unique handle, created_at. Public view exposes handle and a safe public ID only, never email.
- local_campaign_backups: owner, campaign UUID, save schema, revision, payload, timestamp; owner-only; bounded payload and retained versions.
- online_campaigns: owner, campaign UUID, ruleset_version, revision, active planet, server timestamps, canonical progression and session lease.
- online_worlds/chunks: campaign/planet/chart/seed, authoritative cell state, buildings and finite seam ledger. Store durable state separately from loaded render chunks.
- online_inventory: campaign, location (miner/ship/planet+id), ore, quantity_half_units; unique source key; nonnegative constraints.
- online_wallets: campaign, credit_minor, nonnegative. One canonical account currency balance; do not maintain a separately spendable client wallet.
- market_v2_listings: owner/campaign/source provenance, ore, original/remaining half-units, price_minor, state, revision, timestamps.
- market_v2_escrow: exact unfilled reserved ore keyed to listing.
- market_v2_returns: cancellation remainder and claim state, owner/campaign/location provenance.
- economy_operations: owner, UUID idempotency key, operation kind, canonical input hash, status and result receipt.
- economy_ledger: immutable debit/credit lines, reason, operation/listing/counterparty references, balances/revisions where useful. Owner-facing receipts omit other users' private balances.

Request envelope: authenticated user, campaign_id, ruleset_version, expected_revision, operation_id, typed command payload. Derive user identity from verified auth, not a payload user_id. Reuse the same operation ID on network retry; same ID with different input is rejected. Store operation outcome in the same transaction as mutations, so timeout then retry cannot duplicate effects. Never use browser disabled buttons as concurrency control.

Explicit operations: start_campaign; backup_local_save; claim_session; load_online_state; submit_game_commands; create_sell_listing; quote_purchase; purchase_listing; cancel_listing; claim_return; list_market; list_my_orders; list_history. Use bounded cursor pagination, not unlimited table fetches. A quote is informational; settlement revalidates price/revision, availability, wallet, campaign access and capacity. Changed quote returns a refresh-required response, never silently buys at a higher price.

Suggested structured error codes: AUTH_REQUIRED, CAMPAIGN_MODE, STALE_REVISION, SESSION_CONFLICT, INSUFFICIENT_ORE, INSUFFICIENT_CREDITS, HOLD_FULL, LISTING_CHANGED, LISTING_CLOSED, SELF_TRADE, ACCESS_REQUIRED, RATE_LIMITED, INVALID_COMMAND, RULESET_MISMATCH. UI gives a useful next action and preserves entered quantities where safe.

Security boundaries: no browser service-role key; no direct user writes to wallet, escrow, ledger, inventory or canonical rewards. RLS for owner-only state and allowlisted public book reads. SECURITY DEFINER functions must set safe search_path, fully qualify objects and explicitly restrict execute grants. Check nulls/enums/overflow in SQL, not just TypeScript. Validate auth server-side on every mutation; no unsigned JWT decoding as verification. Escape all handles/user text in UI. Redact tokens/emails from logs.

## 7. Verified gameplay work breakdown

Extract economy rules from Phaser-dependent orchestration into deterministic shared functions; do not port all rendering to a backend or duplicate unversioned balance tables in SQL. Server imports a versioned validated rules bundle. Scene methods call a mode-specific command adapter: local implementation preserves existing behaviour; online implementation sends commands and applies server receipts.

Audit every mutation, with a table of file/symbol, source/sink, validation, receipt and test:
- Tile mining and loose drops: canonical seed/cell yield, finite cell destruction once, validated drill capabilities/duration and legal reachable target. Reward and destroyed cell commit together. Loose pickups have stable server IDs and single-claim consumption.
- Movement: implement deterministic authoritative fixed-step movement/collision for reward-relevant commands, accepting ordered input segments with duration caps, server elapsed-time budget and sequence IDs. Reject teleport/path-through-rock/upward drilling. Client rendering may predict; server corrections restore canonical position/state. Never trust reported x/y as proof of access.
- Core extraction/fuel and travel: server reward once, repeated extraction duration, journey cost and return reserve, dock/access, destination allowlist and atomic world switch.
- Building placement/move/dismantle: validate legal site, ownership, support, materials, refund and capacity; no forged structure or free refund cycle.
- Extraction: server time only, 12-hour cap, finite shared seams, ship present only on current world, blocked production not banked. Settle once at mutation boundaries; no per-player always-on worker required.
- Upgrades/modules: costs, prerequisites, ownership once, server stat/capacity effects.
- NPC sales/contracts/service: existing pricing/bonus caps, delivered quantities, once-only milestones, proper source debits. These are credit issuance/sinks and must be governed, not trusted local events.
- Inventory transfers/discard/death/recovery: conservation, allowed sources, capacities and nonrepeatable costs/rewards. Auth refresh/reload cannot revive forfeited ore.
- Imports/reset: no online restore from an arbitrary save. Online reset/archive must not recreate starter balances or duplicate existing assets; defer UI until lifecycle is explicitly safe.

Online requires connectivity for canonical progression. If disconnected, freeze economic commands and show Reconnecting with Retry/Return to local menu. Do not queue unbounded offline mining and later accept it as truth. Local campaign remains playable offline. Server elapsed time may still advance bounded passive production. No online client should visibly claim confirmed resources before receipt.

Use one active gameplay lease per campaign, renewed only while active; market receipts may arrive independently. A second device shows conflict and offers explicit takeover. A lease is not the authority check: revisions and operation IDs remain mandatory. Do not merge two inventory snapshots. Market changes invalidate cached wallet/ship state; queued gameplay commands rebase from server receipts or fail safely.

## 8. Transaction order and conservation

Document one lock order for all RPCs: operation key -> affected campaign rows sorted by UUID -> listing/escrow rows -> inventories/wallets in stable key order. If discovering a counterparty requires a read, read identifier first, acquire locks in order, then re-read/revalidate listing. No fill holding listing then waiting on a campaign that cancel holds while waiting on that listing. Test actual contention; bounded deadlock/serialization retry reuses the same operation ID.

Create: authenticate -> own campaign/revision/access -> settle own production -> enforce active-listing limit under lock -> validate quantity/price -> debit available source -> add escrow/listing -> immutable receipt -> revision increment -> commit.
Purchase: authenticate -> resolve immutable counterpart -> lock in global order -> reject self trade -> settle buyer production so actual ship room is current -> revalidate quote/listing/balance/capacity -> debit buyer credits, credit seller, decrement escrow and listing, add buyer ship ore -> write both ledger sides and receipt -> increment affected revisions -> commit. All or nothing.
Cancel: authenticate/owner -> locks -> read remaining escrow -> mark cancelled with remaining 0 while preserving separate original/filled/cancelled quantities -> place remainder into returns -> receipt/revision -> commit. Repeated cancel returns original result, no second refund.
Claim: authenticate -> locks -> validate access/capacity -> move exact requested half-units from return record to chosen inventory -> receipt -> commit. Partial claims allowed. Claim never creates a new sell listing automatically.

Conservation identities per operation: ore available+escrow+returns changes only through verified mining/production, explicit gameplay consumption/refund or discard; player-player trade changes total currency by zero. NPC rewards/sinks have explicit ledger reasons. Database constraints and assertions enforce nonnegative balances and exact fill/cancel sums.
